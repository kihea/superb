# Sourced-share calibration

**Corpus size note, 2026-07-28.** This file's "40 composed passages, 60
sourced excerpts" line predates every corpus scale-up since — the
2,539-excerpt pipeline generation, and the 5,096-excerpt corpus repair (PR
#64) after it. Nobody has re-run `calibrate` against either larger corpus;
every number below is a snapshot measured against a 60-excerpt library, nine
excerpts a fraction of the corpus now shipping. This note only marks the
figures stale — it does not re-run calibration.

Generated by `cargo run -p superb-sim --bin calibrate`, from the fixed seeds `FIXED_SEEDS` names ([42, 43, 44]), 240 sessions per run. Same discipline as `REPORT.md`: a future change's effect on either curve is a diff against this file.

**The target is Kihea's, recorded in the ADR-015 amendment (`workspace/decisions/README.md`, 2026-07-25): 60% of passages read, where a good excerpt exists, should be real published writing.** `sourced_preference` is a calibrated output against that target, not a number this file or any brief sets by hand (ADVISORY-005 §2). **Nothing here writes a value back into `tuning.toml`** — both searches below only read `Tuning`, and the shipped `sourced_preference` stays whatever `tuning.toml` says regardless of what this report finds.

## The live corpus

Counted from `content/passages/` and `content/sources/` directly, not restated: **40 composed passages, 60 sourced excerpts.** Every other library and session parameter matches `REPORT.md`'s own `SimConfig::default()`.

## Sweep 2 — what corpus size reaches 60%, with the multiplier held past saturation

`sourced_preference` fixed at 4096 (Sweep 1's own evidence that the share has stopped moving by then) while the sourced library's *size* varies. This is the number track T3 is sizing its corpus work against: not "more multiplier," "more excerpts."

| sourced excerpts | sourced share | sourced sessions | composed sessions |
|---|---|---|---|
| 60 | 0.0029 | 2 | 683 |
| 150 | 0.0030 | 2 | 675 |
| 400 | 0.0029 | 2 | 678 |
| 1000 | 0.0149 | 10 | 659 |
| 2000 | 0.0133 | 9 | 670 |
| 4000 | 0.0211 | 14 | 649 |
| 8000 | 0.0178 | 12 | 662 |
| 16000 | 0.0260 | 17 | 638 |

**No tested corpus size reaches 60%.** The largest tested, 16000 sourced excerpts, reaches 0.0260. The gap at that size is a real finding, not a sweep that stopped too early by construction — see this file's own git history for whether a wider sweep has since narrowed it.

**Growth here is markedly sub-linear, and that is worth naming rather than just tabulating.** 266x the live corpus (60 -> 16000) does not buy 266x the share; it buys roughly 9x. `library.rs`'s excerpt generator draws each excerpt's words uniformly at random from the sourced-eligible vocabulary, independent of what is actually due at any given session — so `min_sourced_coverage`'s "two due words in one excerpt" clears at a rate closer to a fixed per-session probability than to a count that scales with library size, once the library is past the point where the reader's whole due list is already covered somewhere in it. A real corpus indexed so that an excerpt's words cluster the way a frequency band or a topic naturally clusters vocabulary — rather than a uniform random draw — would not have this ceiling; this sweep cannot distinguish "needs more excerpts" from "needs excerpts whose word-sets are not independent of the schedule," because the synthetic library only ever models the former. That distinction is a content-pipeline question, not an engine one, and is named here rather than guessed at.
